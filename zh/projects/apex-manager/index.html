Case File / Harness Evidence

apex-manager

跨终端会话调度并行 AI Worker 的多 Agent 编排案例。

Orchestration case-study GitHub repo

Problem

很多多 Agent 产品会直接复制人类组织架构：PM Agent、架构师 Agent、开发 Agent、测试 Agent。表面上分工很完整，实际却因为不断交接而丢失上下文。

真正的问题不是角色数量，而是如何在多个完整 Worker 并行推进时保住全局意图、任务状态、依赖顺序和隔离。

Why It Matters

真实工程任务里，并行会带来文件冲突、重复劳动、依赖混乱和责任不清。Agent Harness 需要把这些问题显式化，而不是靠聊天窗口记住。

Product Thesis

多 Agent 编排不应该是角色扮演，而应该是 Team Kernel：Plan Agent 保持全局意图，Worker 独立完成完整任务闭环，验证作为对抗性工作模式存在。

My Role / Judgment

我的判断是先做状态和控制语义，而不是先做 dashboard。apex-manager 因此是 terminal-first、local-first，站在已有 Claude / Codex / Gemini CLI 之上。

Architecture

四层结构：

  1. Plan Agent：拆任务、排依赖、分配 Worker、综合结果。
  2. Worker：理解、实现、验证、自查和汇报。
  3. Review mode：独立评审和对抗检查，而不是继续接棒生产。
  4. Daemon / State：通过 .apex-manager/ 维护 task、message、artifact、event。

Design Tradeoffs

我选择轻量编排层，而不是重后台；选择显式自动化，而不是默认加入 full-auto 或 yolo 权限绕过。

What I Built

  • 本地多 Agent 编排器。
  • task / dependency / message / artifact / event 语义。
  • daemon 和状态账本。
  • worktree-oriented 并行隔离。
  • terminal / tmux 友好的运行方式。

Evidence

公开 repo 把它描述为跨终端 session 管理并行 AI Worker 的独立 multi-agent orchestrator，并强调 Plan Agent、完整 Worker、独立评审和 .apex-manager/ 状态层。

What I Learned

多 Agent 的难点不是多开几个模型，而是在并行时维持意图、状态和责任。

Status

Prototype / usable local orchestrator。

Next

下一步是强化 task/artifact 语义、review workflow、运行历史，并为 MCP / A2A / ACP 等 transport 留接口。

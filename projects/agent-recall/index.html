Case File / Harness Evidence

agent-recall

Persistent memory and session continuity across AI coding agents, tools, projects, and users.

Memory case-study GitHub repo

Problem

AI coding agents forget the work context between sessions. They also fragment memory across tools: Claude Code knows one thing, Codex another, Cursor another, and Gemini another. The user becomes the memory bus.

That does not scale if Agents are expected to become persistent collaborators rather than disposable chat windows.

Why It Matters

Real Agent products need continuity. They need to know who the user is, what project is active, what the current task was, what has already been tried, and what knowledge should be promoted from a project to global memory.

Without a memory harness, every new session pays the same context reconstruction tax. Worse, important preferences and project facts stay trapped inside one tool or one transcript.

Product Thesis

Agent memory is not chat history. It is structured continuity across tools, sessions, projects, users, persona, active tasks, retrieval, and promotion.

A useful memory layer should be platform-agnostic at the core and adapter-specific at the edges.

My Role / Judgment

The product judgment was to separate memory semantics from any single agent host. Rather than treating one tool as canonical, agent-recall treats memory as shared infrastructure that different coding agents can read from and write to.

The second judgment was to split memory into layers: global user memory, project-scoped observations, active task recovery, session archives, and promotion rules. That keeps memory useful without turning it into an undifferentiated transcript dump.

Architecture

The architecture has a thin adapter layer for agent platforms and a shared core underneath:

  1. Platform adapters for Claude Code, Cursor, Codex CLI, Gemini CLI, OpenCode, and related hosts.
  2. A local worker HTTP API.
  3. Business logic for persona, bootstrap interview, active task recovery, memory layering, promotion, archives, and search.
  4. SQLite / FTS-based storage with optional vector search where configured.

The core idea is that most memory behavior should be platform-agnostic. Each new host should need a thin adapter, not a new memory product.

Design Tradeoffs

I chose structured summaries over raw transcript storage as the primary memory unit. Raw logs are too noisy for every new session; structured observations are easier to inject, search, and promote.

I also treated “who the Agent is” and “who the user is” as product primitives. That can sound soft, but it changes behavior: a long-lived assistant needs a stable collaboration profile and a way to recover active work.

The tradeoff is complexity. Memory systems can become intrusive or stale. That is why scoping, promotion policy, and explicit recovery flows matter.

What I Built

  • Shared memory across Claude Code, Cursor, Codex CLI, Gemini CLI, and OpenCode.
  • Lifecycle hook capture for tool executions.
  • AI compression into structured observations.
  • Context injection at session start.
  • Agent persona and user profile bootstrap.
  • Active task recovery.
  • Global and project-scoped memory layers.
  • Memory promotion from project facts to reusable global knowledge.
  • Searchable archives and temporal recall.

Evidence

The repo describes a shared SQLite database used across multiple agent platforms. It includes platform adapters, a worker API, persona/bootstrap/recovery logic, memory layering, promotion, archives, and search.

The README states that 70-80% of the code is platform-agnostic and that new platforms should only require a thin adapter. That supports the product thesis that memory belongs to the harness, not to a single model UI.

What I Learned

Memory quality is mostly a product problem. The hard questions are what to capture, when to compress, what to inject, when to promote, and how to prevent stale or overbroad context from polluting new work.

The memory layer also reveals a bigger principle: Agent continuity should be explicit infrastructure, not an accidental side effect of longer context windows.

Status

Alpha / usable prototype. The core pipeline and platform model exist, but the product should continue improving observation quality, adapter validation, and memory governance.

Next

The next step is stronger evaluation for memory usefulness: whether injected context actually helps the Agent resume work, avoid repeated mistakes, and preserve user/project preferences without overfitting to old state.

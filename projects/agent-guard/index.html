Case File / Harness Evidence

agent-guard

Deterministic security interception layer for AI Agents using low-latency gates outside the model loop.

Security / Control case-study GitHub repo

Problem

Prompt rules are not a control system. A model can be instructed to behave safely, but important safety rules need enforcement outside the model’s own reasoning and prompt-following loop.

At the same time, fully caging an Agent can make it useless. If every meaningful action becomes a confirmation dialog, the Agent becomes a script that needs a babysitter.

Why It Matters

Real Agent products need to act. They need access to files, terminals, tools, secrets, and workflow systems. That means the product problem is not “never let the Agent do anything.” It is allowing useful work while gating irreversible or suspicious actions.

Agent safety should be a harness capability: deterministic, low-latency, auditable, and difficult for the Agent to bypass.

Product Thesis

Security should sit in the pipeline, not inside the Agent’s self-description.

The Agent can propose actions, but every sensitive action should pass through deterministic gates that evaluate command risk, path sensitivity, trust, anomaly, and combined signals before execution.

My Role / Judgment

The core judgment was to move from prompt-based safety to hook-based control. A hook sees the actual tool call. The model cannot negotiate with it, forget it, or rephrase around it.

The second judgment was to use layered defense. No single rule catches every risk. A harness needs multiple independent layers whose blind spots do not align.

Architecture

agent-guard installs as Claude Code PreToolUse and PostToolUse hooks.

The engine has five layers:

  1. Hard rules for deterministic known-risk patterns.
  2. Path safety for file and directory sensitivity.
  3. Trust evaluation based on safe operation history and violations.
  4. Rate and anomaly detection for bursts or behavior shifts.
  5. Synthesis that aggregates signals in a Swiss Cheese style decision layer.

The PostToolUse side also sanitizes credential-like output before it is returned to the Agent.

Design Tradeoffs

I chose deterministic hooks over MCP tools or prompt policies because tools and skills are still optional from the model’s point of view. A hook is in the execution path.

I chose low-latency local checks over heavyweight ML scanning for the first layer. Agent control needs to run often, so the normal path must be cheap.

I also avoided binary thinking. Some operations should be denied, some allowed, and some confirmed depending on path, trust, and signal combination.

What I Built

  • A hook-based security interception layer for Agent tool calls.
  • A 5-layer decision engine with hard rules, path safety, trust, anomaly, and synthesis.
  • Built-in deterministic rules for dangerous commands, sensitive paths, credentials, and injection patterns.
  • Credential sanitization for tool output.
  • Trust management, audit log, rule management, and configuration commands.
  • Benchmarks and test cases described in the repo documentation.

Evidence

The public repo describes agent-guard as a deterministic security interception layer with zero runtime dependencies, 32 built-in rules, a 5-layer Swiss Cheese engine, and P99 latency under 1ms for the full pipeline.

The README explains why hook-based interception is different from MCP or skill-based safety: the Agent cannot see or bypass the hook in the same way it can ignore an optional instruction.

What I Learned

Agent safety is a product design problem, not only a security checklist. The right user experience is not “block everything.” It is to preserve useful autonomy while making dangerous transitions deterministic, visible, and auditable.

The most important shift is moving control from text to infrastructure.

Status

Prototype / usable security layer for Claude Code hook workflows. It demonstrates the control thesis clearly, but broader agent-host support and more adversarial validation would make it stronger.

Next

The next step is wider host compatibility, richer policy configuration, stronger false-positive analysis, and integration with skill/MCP scanners so runtime control and supply-chain review work together.

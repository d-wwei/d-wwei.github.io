Case File / Harness Evidence

apex-manager

Multi-agent orchestration for parallel AI workers across terminal sessions.

Orchestration case-study GitHub repo

Problem

Most multi-agent products start by copying a human org chart: one Agent plays PM, one plays architect, one writes code, one tests. The result looks organized, but the work often becomes worse as it passes through more role boundaries.

The missing product problem is not “more roles.” It is preserving global intent while multiple full-stack workers move in parallel without stepping on each other.

Why It Matters

Agent teams fail when context handoffs compress the real reasoning: why a path was chosen, which tradeoff was rejected, what is fragile, and what still needs review. For real engineering work, parallelism also creates file conflicts, duplicate effort, hidden task dependencies, and unclear ownership.

An Agent harness needs orchestration semantics: task state, dependency order, worker isolation, artifact tracking, and independent review modes.

Product Thesis

Multi-agent orchestration should behave less like a fake company and more like a local Team Kernel.

The Plan Agent should keep global intent, split work, order dependencies, and synthesize results. Worker agents should remain complete engineers who can understand, implement, verify, and self-review their assigned task. Verification should be an adversarial work mode, not another lossy handoff stage.

My Role / Judgment

The key product judgment was to avoid “role cosplay.” I treated orchestration as a control and state problem, not a character design problem.

That led to a terminal-first, local-first system that sits above existing CLI agents instead of replacing them. The user keeps using Claude, Codex, Gemini, or other agent CLIs, while apex-manager provides shared task, message, artifact, and event semantics.

Architecture

The architecture has four layers:

  1. Plan Agent: holds global intent, breaks work into tasks, orders dependencies, assigns workers, and integrates results.
  2. Worker agents: run full task loops in isolated contexts.
  3. Review mode: sends independent workers to audit, test, or challenge outputs instead of continuing the production handoff chain.
  4. Daemon / state layer: externalizes coordination into .apex-manager/ through tasks, messages, artifacts, and events.

The project is terminal-first. When possible, workers can use separate worktrees so parallelism is backed by filesystem isolation, not just conversational agreement.

Design Tradeoffs

I chose a thin orchestration layer instead of a heavy dashboard. The goal was to make multi-agent work usable from the environment where coding agents already live: the terminal.

I also avoided making auto-approval the default. A serious Agent orchestrator should not quietly add --full-auto, --yolo, or equivalent permission bypass behavior. Automation can exist, but it should be explicit and controlled.

The current product surface is more kernel-like than manager-like: it prioritizes state, task dependency, and worker execution semantics over polished visual operations.

What I Built

  • A local multi-agent orchestrator for parallel AI Worker agents across terminal sessions.
  • Plan/worker workflow semantics with task creation and dependency ordering.
  • A daemon and event ledger to keep task and worker state outside chat memory.
  • Message and artifact coordination primitives.
  • Worker isolation patterns, including worktree-oriented parallelism where applicable.
  • Terminal and tmux-friendly execution flow for real local development work.

Evidence

The public repo describes apex-manager as an independent multi-agent orchestrator that manages parallel AI Worker agents across terminal sessions. Its README frames the system around a Plan Agent, complete Worker agents, independent review work, and a daemon/state layer in .apex-manager/.

The repo also explicitly states that automatic full-auto or permission-skipping flags are not enabled by default. That is important evidence of the control philosophy behind the orchestrator.

What I Learned

The hardest part of multi-agent product design is not spawning more agents. It is preserving intent, state, and accountability as work becomes parallel.

The strongest worker unit is usually not a narrow role. It is a complete task owner with enough context to reason, implement, verify, and report. The harness should make that safe and coordinated.

Status

Prototype / usable local orchestrator. It is strong enough to express the product thesis and run local multi-agent work, but it should still be treated as an evolving Team Kernel rather than a finished platform.

Next

The next product step is to harden task/artifact semantics, improve review workflows, add clearer run history, and prepare the kernel for richer transports such as MCP, A2A, ACP, or remote workers without losing terminal-native simplicity.
